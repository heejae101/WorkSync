# 팀 룰

## 목적
회사도우미 프로젝트를 팀원들이 같은 기준으로 분석, 설계, 개발, 학습하기 위한 기본 규칙을 정의한다.

## 기본 원칙

- 문서 먼저, 구현은 그 다음에 진행한다.
- 작은 단위로 작업하고 자주 공유한다.
- 모르는 내용은 숨기지 말고 학습 기록이나 미결정 사항으로 남긴다.
- 기술 선택은 이유를 남긴다.
- 회의에서 결정된 내용은 당일 문서에 반영한다.

## 커뮤니케이션 규칙

| 상황 | 규칙 |
|---|---|
| 요구사항 변경 | 요구사항 정의서와 관련 설계 문서를 같이 수정한다. |
| 설계 변경 | 변경 이유, 영향 범위, 대안을 기록한다. |
| 버그 발견 | 재현 방법, 기대 결과, 실제 결과를 남긴다. |
| 기술 조사 | 링크만 공유하지 말고 요약과 적용 가능성을 함께 쓴다. |
| 막힌 작업 | 에러 메시지, 시도한 방법, 현재 가설을 공유한다. |

## 문서 작성 규칙

- 확정된 내용은 `확정`으로 적는다.
- 아직 정하지 않은 내용은 `미결정` 또는 `검토 필요`로 적는다.
- 표를 사용할 수 있으면 표로 정리한다.
- 화면, API, DB, 테스트는 요구사항 ID와 연결한다.
- 변경 이력이 있는 문서는 하단에 변경 이력을 둔다.

## 작업 완료 기준

작업은 다음 조건을 만족해야 완료로 본다.

- 관련 문서가 갱신되어 있다.
- 구현이 있다면 테스트 또는 검증 방법이 있다.
- 미결정 사항이 남아 있으면 다음 액션이 적혀 있다.
- 팀원이 이해할 수 있는 설명이 남아 있다.

## 회의 룰

- 회의 전: 논의할 안건을 문서로 준비한다.
- 회의 중: 결정, 보류, 액션 아이템을 분리해서 기록한다.
- 회의 후: 담당자와 기한을 정한다.
