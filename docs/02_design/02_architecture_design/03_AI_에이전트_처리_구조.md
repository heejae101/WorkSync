# AI 에이전트 처리 구조

## 문서 목적

- 회사도우미의 AI 처리를 단순 API 호출이 아니라 에이전틱 처리 구조로 설계한다.
- 회의록과 시간 기록 대시보드가 같은 앞단 기능을 공유한다는 점을 명확히 한다.
- AI 실행 방식을 터미널 세션 브리지, OAuth 연동, 로컬 모델 3개 후보로 비교한다.

## 공통 음성 처리 파이프라인

회의록과 시간 상담/기록 대시보드는 앞단 입력 흐름이 같다.

```text
[사용자]
   |
   | 음성 녹음 또는 파일 업로드
   v
[Audio Intake]
   |
   | 파일 검증, 저장, 작업 생성
   v
[STT]
   |
   | 원문 텍스트 생성
   v
[Transcript]
   |
   | 사용자가 목적 선택 또는 AI가 후보 추천
   v
[Agent Router]
   ├── Meeting Minutes Agent
   └── Time Log Agent
```

## 목적별 AI 처리

| 목적 | 입력 | AI 결과 | 저장 위치 |
|---|---|---|---|
| 회의록 작성 | 음성 원문 텍스트, 참여자 별칭, 세션 이름 | 안건, 결정사항, 할 일, 담당자, 마감일, 요약문 | `meeting_summaries`, `session_files.content_markdown/json` |
| 시간 기록 | 음성 원문 텍스트, 날짜, 폴더/파일 정보 | 시간대, 활동명, 활동 유형, 중요도/집중도 가중치, 일간/주간 요약 | `time_logs`, `session_files.content_json` |

회의록은 “무엇을 결정했고 누가 무엇을 해야 하는가”가 핵심이다.

시간 기록은 “시간을 어디에 썼고 어떤 가중치로 볼 것인가”가 핵심이다.

## 에이전트 후보

| 에이전트 | 책임 |
|---|---|
| `AudioIntakeAgent` | 업로드 파일 검증, 녹음 메타데이터 정리, STT 작업 생성 |
| `TranscriptAgent` | STT 결과 정리, 문장 보정, 발화 구간 정리 |
| `MeetingMinutesAgent` | 회의록 구조화, 결정사항/할 일/담당자/마감일 추출 |
| `TimeLogAgent` | 활동 시간 분류, 중요도/집중도 가중치 제안, 대시보드 데이터 생성 |
| `DeadlineAgent` | 회의록/시간 기록에서 일정과 마감 후보 추출 |
| `ReportAgent` | 주간 보고서 초안 생성 |

## AI 실행 방식 후보

### 후보 A: 터미널 세션 브리지

이미 켜놓은 터미널 AI 세션에 API 요청 내용을 그대로 입력하고, 터미널 출력 결과를 다시 읽어 응답으로 반환하는 방식이다.

```text
Spring API
-> AI Bridge
-> Terminal Session
-> AI CLI
-> Terminal Output
-> Spring API
```

장점:

- 빠르게 실험할 수 있다.
- 이미 사용하는 CLI 세션을 재사용할 수 있다.
- API Key를 애플리케이션 서버에 바로 넣지 않아도 되는 실험 환경을 만들 수 있다.

리스크:

- 터미널 출력 파싱이 깨지기 쉽다.
- 동시 요청, 타임아웃, 세션 끊김, 재시도 처리가 어렵다.
- 제품 기능으로 두기에는 감사 로그와 장애 대응이 약하다.
- 사용자 요청이 그대로 터미널에 입력되므로 명령 실행/프롬프트 인젝션 경계가 흐려진다.

판단:

- 개발 실험용으로만 사용한다.
- MVP 제품 구조의 기본 선택지는 아니다.

### 후보 B: OAuth 또는 외부 서비스 연동

사용자가 외부 서비스 권한을 연결하고, 시스템이 허용된 범위 안에서 API를 호출하는 방식이다.

```text
Spring API
-> OAuth Consent
-> Provider Token
-> External AI/API Provider
-> Result
```

장점:

- 사용자별 권한 위임 흐름을 만들 수 있다.
- GitHub, Google Drive, Notion 같은 외부 자료 접근이 필요할 때 자연스럽다.
- 사용자별 감사와 권한 철회 모델을 만들기 좋다.

리스크:

- LLM 호출 자체는 보통 OAuth보다 API Key 또는 서버 측 토큰 방식이 단순하다.
- OAuth 토큰 저장, 갱신, 철회, scope 관리가 필요하다.
- 초반 구현량이 커진다.

판단:

- GitHub/Notion/Google 같은 외부 데이터 연동에는 적합하다.
- 순수 LLM 요약/분류 호출의 1차 선택지는 아니다.

### 후보 C: 로컬 모델

Ollama 또는 로컬 LLM/STT를 서버 또는 개발 PC에서 실행하고, Spring/Python Worker가 로컬 endpoint를 호출하는 방식이다.

```text
Spring API
-> Python AI Worker
-> Local STT/LLM
-> Result
```

장점:

- 민감한 음성/회의 내용을 외부 API로 보내지 않을 수 있다.
- 비용 예측이 쉽다.
- 오프라인 또는 제한된 네트워크 환경에서 실험 가능하다.

리스크:

- 품질과 속도가 하드웨어에 크게 좌우된다.
- 모델 설치, 업데이트, GPU/메모리 관리가 필요하다.
- 회의록 품질이 외부 상용 API보다 낮을 수 있다.

판단:

- 보안이 중요한 데이터에는 유리하다.
- MVP에서는 품질 검증이 필요하다.

## MVP 권장 방향

MVP는 다음 순서로 간다.

1. 공통 음성 처리 파이프라인을 먼저 만든다.
2. AI 호출은 `Python AI Worker` 뒤에 감춘다.
3. Worker 내부 실행 방식은 설정으로 바꿀 수 있게 한다.
4. 1차 구현은 외부 AI API 또는 로컬 모델 중 하나를 선택한다.
5. 터미널 세션 브리지는 개발 실험용으로만 둔다.
6. OAuth는 GitHub/Notion/Google 같은 외부 자료 접근이 실제로 필요해질 때 도입한다.

핵심은 Spring Backend가 특정 AI 실행 방식에 묶이지 않는 것이다.

```text
Spring API
-> ai_jobs 생성
-> Python AI Worker
-> provider_adapter 선택
   ├── external_api
   ├── local_model
   └── terminal_bridge(dev only)
-> ai_results 저장
```

## 미결정 사항

| 항목 | 선택지 | 영향 |
|---|---|---|
| 1차 AI 실행 방식 | 외부 API, 로컬 모델 | 품질, 비용, 보안 |
| STT 방식 | 외부 STT API, 로컬 STT | 전사 품질과 처리 속도 |
| Agent 프레임워크 | 직접 구현, LangGraph, 기타 | 구현 난이도와 확장성 |
| 시간 기록 가중치 기준 | 중요도, 집중도, 긴급도, 업무 유형 | 대시보드 해석 방식 |
| 터미널 브리지 사용 범위 | 사용 안 함, 개발 실험용만 | 안정성과 보안 |
